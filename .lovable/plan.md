## Проблема

Ошибка "new row violates row-level security policy for table mechanic_shifts" — таблица `mechanic_shifts` в БД имеет политику доступа только для авторизованных пользователей (`TO authenticated`), а в приложении вход/авторизация не используется — все запросы идут анонимно. Поэтому создание смен из клика по календарю падает.

При проверке нашлись ещё две таблицы с той же несогласованностью:
- `mechanic_shifts` — авторизованные, а не публичные
- `mechanic_service_rates` — авторизованные (влияет на ставки мастеров)
- `client_reminders` — авторизованные (влияет на напоминания клиентам)

Остальные 9 таблиц (`appointments`, `clients`, `cars`, `mechanics` и т.д.) уже публичные, поэтому основное приложение работает.

## Что сделаю

Одна миграция — привести три таблицы к тому же режиму, что и остальные (полный доступ без авторизации, как сейчас во всём проекте):

- Удалить старые политики "authenticated ..." на `mechanic_shifts`, `mechanic_service_rates`, `client_reminders`.
- Создать новые политики `FOR ALL TO public USING (true) WITH CHECK (true)` — по образцу существующих политик на остальных таблицах.
- GRANT-ы этим таблицам уже есть (иначе даже чтение бы не работало), новых выдавать не нужно.

После миграции клик по слоту календаря сразу создаст смену выбранного мастера без ошибок.

## Предупреждение о безопасности

Сейчас вся БД проекта открыта без авторизации — любой человек, знающий publishable-ключ, может читать и писать все данные. Это подходит для внутреннего инструмента, но если планируется публикация — стоит отдельно добавить вход и переключить политики на `auth.uid()`.
