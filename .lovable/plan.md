
## Проблема (что подтвердил аудит кода)

Сейчас в `src/routes/expenses.tsx`:
- «Оборот» месяца = `sum(paid_amount)` по записям с `starts_at` в этом месяце.
- «ЗП начислено» = `sum(mechanic_payout)` по тем же записям.
- «Прочие расходы» и «Авансы» — по своим датам (`spent_at` / `paid_at`).

Из-за этого прибыль «скачет» между месяцами в трёх сценариях:

1. **Частичная оплата.** Клиент отдал часть в январе, часть в феврале. Поле `paid_amount` одно — вся сумма попадает в месяц `starts_at` (январь), в феврале не видно ничего. Если потом дописать `paid_amount`, январский «оборот» задним числом вырастет.
2. **Оплата в другом месяце.** Работа сделана в январе (`starts_at`), оплачена в феврале. Оплата всё равно уедет в январь — февраль «пустой», январь задним числом «оживает».
3. **Аванс с задержкой.** Начисление уже учитывается по `starts_at`, а выплата по `paid_at` — сама логика ок, но нет привязки аванса к конкретным работам, поэтому «долг мастеру» и «выплачено» живут в разных месяцах и сходятся только суммарно, не по периоду.

## Что делаем

### 1. Журнал платежей клиента (миграция)

Таблица `appointment_payments`: `appointment_id`, `paid_at date`, `amount`, `method` (nullable), `note`. GRANT + RLS + триггер `updated_at`.

- Триггер: после INSERT/UPDATE/DELETE пересчитывает `appointments.paid_amount = SUM(amount)` и `payment_status` (`unpaid` / `partial` / `paid`) по сравнению с `total_price`.
- Бэкфилл: для каждой существующей записи с `paid_amount > 0` вставить один платёж с `paid_at = starts_at::date`, чтобы история не потерялась.

### 2. API и UI платежей

- В `src/lib/api.ts`: `listAppointmentPayments(appt_id)`, `createAppointmentPayment`, `deleteAppointmentPayment`, `listPaymentsRange(from, to)`.
- В `AppointmentDialog`: заменить одиночное поле «Оплачено» на мини-журнал платежей (дата + сумма + удалить), плюс кнопка «Оплачено полностью сегодня». Итог `paid_amount` показываем как read-only.
- В `schedule.tsx` кнопка «Оплатить» открывает тот же мини-журнал (быстрая запись платежа сегодняшним днём).

### 3. Кассовый учёт в «Расходах»

`src/routes/expenses.tsx`:
- **Оборот месяца** = `sum(appointment_payments.amount)` где `paid_at` в месяце (независимо от `starts_at`).
- **ЗП мастерам — начислено** оставляем по `starts_at` (обязательство сервиса), это правильно и не скачет.
- **ЗП мастерам — выплачено** = авансы за месяц.
- **Прочие расходы** — как сейчас, по `spent_at`.
- **Чистая прибыль (касса)** = оборот(платежи) − начисленная ЗП − прочие расходы. Прибыль перестаёт зависеть от того, когда именно клиент донёс остаток и когда выплатили аванс.
- Добавить строку «Выполнено, ждём оплату» = `sum(total_price − paid_amount)` по `done` за месяц — чтобы видеть «зависшую» дебиторку, но не мешать её с прибылью.

### 4. Проверка сценариев (ручные тесты в конце)

Пройти три кейса на реальных данных и убедиться, что цифры не «скачут»:
- частичная оплата на стыке месяцев;
- работа в одном месяце, полная оплата в следующем;
- аванс мастеру, выплаченный через месяц после работ.

## Что НЕ трогаем

- Логика авансов/долга мастеру (уже правильная — учитываем начисление, а выплата отдельно).
- Раздел «По мастерам»/«По услугам» — только пересчёт агрегатов, структура та же.
- RLS/аутентификация, синхронизация оффлайн — вне этой задачи.

## Технические детали

- Миграция: `CREATE TABLE public.appointment_payments (...)` + `GRANT SELECT, INSERT, UPDATE, DELETE ON public.appointment_payments TO authenticated; GRANT ALL ... TO service_role;` + `ENABLE ROW LEVEL SECURITY` + открытая политика (в проекте пока нет auth — совместимо с текущими таблицами) + триггер пересчёта `paid_amount`/`payment_status` + триггер `updated_at`.
- Бэкфилл в той же миграции: `INSERT INTO appointment_payments (appointment_id, paid_at, amount) SELECT id, starts_at::date, paid_amount FROM appointments WHERE paid_amount > 0;`
- В `listAppointments` ничего менять не нужно (paid_amount кэшируется триггером); для «Расходов» добавить отдельный запрос платежей по диапазону.
