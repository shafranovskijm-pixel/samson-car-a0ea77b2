## Что нашли (аудит)

Проверил потоки: запись → услуги/выплата мастеру → платежи клиента → раздел «Расходы» → карточка мастера. База сейчас: 6 строк услуг, из них **4 с `mechanic_payout = 0`** (старые/из калькулятора). Именно из-за них расчёты ЗП и прибыли расходятся между экранами.

### Реальные проблемы (по важности)

1. **Смешанная формула прибыли в «Расходах».** Сейчас:
   `profit = revenue(касса) − mechanicsAccrued(начислено) − otherExpenses(касса)`.
   Оборот и расходы — кассовый метод, ЗП — начисление. Из-за этого прибыль скачет между месяцами: работа июля оплачена в августе → в июле «минус на всю ЗП», в августе «плюс на всю кассу». Пользователь уже жаловался на это раньше.

2. **Три разные формулы ЗП мастера** в одном приложении:
   - `AppointmentDialog.rateFor`: stored → mech% → service% → 50%.
   - `expenses.effPayout`: stored → mech% → 50% (игнорирует % услуги).
   - `mechanics.MechanicSalary.effPayout`: stored → `defaultPercent` мастера → 50% (игнорирует % услуги).
   Значит в «Расходах» и в карточке мастера одна и та же строка может дать разную ЗП, если у услуги стоит собственный %.

3. **«Долг мастерам» в шапке клэмпится в 0** (`max(0, начислено − авансы)`), а в раскрытой таблице «По мастерам» — показывается как отрицательный (красный «К выплате −N»). Одна и та же сумма выглядит по-разному.

4. **UI-дубль в карточке мастера.** В `MechanicShifts` два одинаковых заголовка/кнопки подряд: «График смен» и «График работы» с двумя кнопками «Смена». Визуальный баг.

5. **Опасные операции без подтверждения.**
   - «Сбросить оплату» в `/schedule` (dropdown платежа) — сносит все платежи по записи одним кликом.
   - Удаление платежа в `PaymentsSection` — тоже без подтверждения.
   - В `mechanics.tsx` используются нативные `window.confirm` (удаление мастера, аванса), хотя в проекте уже есть `ConfirmProvider` — рассинхрон стиля.

6. **`Ждём оплату`** использует `paid_amount` (совокупный по всем месяцам), поэтому по записи месяца, за которую клиент доплатит через полгода, «остаток» останется висеть — визуально не ошибка, но не бьётся с кассовым оборотом.

### Что НЕ трогаем в этом заходе

- Расчёт `revenue` по `appointment_payments.paid_at` — корректный, оставляем.
- Триггеры `recompute_appointment_total`, `recompute_appointment_payment` — работают.
- «Максимум обновлений превышен» из логов — стек Radix `setRef`, стабильного репро нет; починим после того, как воспроизведётся; сейчас не гадаем.

## План правок

### 1. Единый хелпер ЗП `src/lib/payouts.ts`
Вынести общую функцию:

```ts
effectivePayout({ storedPayout, price, mechanic, service }) →
  stored>0 ? stored
  : mech.default_payout_percent>0 ? price*mech%/100
  : service.default_payout_percent>0 ? price*svc%/100

```

Использовать везде: `AppointmentDialog.rateFor`, `expenses.effPayout`, `mechanics.MechanicSalary.effPayout`. Мастера/услуги грузим уже везде, где нужно.

### 2. Прибыль: две согласованные метрики вместо одной смешанной

В шапке `/expenses` заменить герой-карточку на две согласованные:

- **Прибыль (кассовая)** = `revenue − advances_paid_month − otherExpenses`. Что реально «в кармане» за месяц.
- **Прибыль (начисленная)** = `Σ done.total_price(month) − mechanicsAccrued(month) − otherExpenses(month)`. Что заработали по факту выполненных работ.

Хвост-карточек оставляем: Оборот кассы, Ожидается, Ждём оплату, ЗП начислено, Долг мастерам, Прочие. У «Долг мастерам» убрать `max(0,…)` — показывать реальное число (может быть отрицательным = «переплатили авансами»), синхронно с раскрытой таблицей.

Подписи под цифрами явно называют метод (касса/начисление), чтобы больше не путать.
