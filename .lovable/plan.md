## Что происходит сейчас

**Калькулятор** (кнопка «Добавить услугу» внутри категории, только для выбранного авто):
- Услуга сохраняется в `car_custom_services` с ключом (марка, модель, год, категория, название).
- При повторном добавлении с тем же названием — цена молча перезаписывается, дубля нет.
- Пользователь не получает обратной связи: непонятно, добавилось новое или обновилось старое.
- Если сохранение падает — общий `alert("Не удалось сохранить (нужно войти)")`, даже когда причина другая.

**Запись** (AppointmentDialog, «Своя услуга»): live-детекция уже есть, дубли ловятся, сообщение «Такая услуга уже есть» показывается.

## Что поправить (только UX калькулятора)

1. **Показать понятный toast после сохранения кастомной услуги** для авто:
   - если такой (категория+название) уже был у этой машины — «Цена обновлена: {название} — {новая цена} ₽»
   - если новая — «Добавлено для {Марка Модель Год}: {название}»
2. **Живая подсказка при вводе названия** в форме «своей услуги»: если в текущих `customServices.items` (той же категории) уже есть точное совпадение по названию — показать под инпутом плашку «Уже есть, цена {старая} ₽ — сохранение перезапишет цену». Пользователь видит это до нажатия «Сохранить».
3. **Нормальные сообщения об ошибках** вместо `alert(...)`: заменить на `toast.error(...)` с текстом Supabase (использовать уже существующий хелпер перевода из `AppointmentDialog.tsx`, вынести в `src/lib/api.ts` как `humanizeSupabaseError`, чтобы использовать и в калькуляторе).
4. **Ничего не трогать в схеме БД** — уникальный индекс (brand,model,year,category,name) уже даёт правильную семантику «одна услуга с таким именем на одну связку авто».

## Что НЕ делаем

- Не меняем структуру `car_custom_services` и `services`.
- Не трогаем логику записи (AppointmentDialog) — там уже нормально.
- Не объединяем глобальные `services` с кастомными — они специально разделены: глобальные для справочника/статистики, кастомные привязаны к машине.
